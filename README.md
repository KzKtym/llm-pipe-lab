# llm_pipe_lab

[![test](https://github.com/KzKtym/llm-pipe-lab/actions/workflows/test.yml/badge.svg)](https://github.com/KzKtym/llm-pipe-lab/actions/workflows/test.yml)


このリポジトリは、「売上戦略を相談できるシステム」を成立させる土台  
**—— NL→SQL パイプラインと、その答えの正しさを測る評価基盤 ——**   
の技術検証(LLM Pipeline Lab.)を掲載しています。

パイプラインで日本語の業務質問を SQL に変換して実行し、  
評価基盤でその結果を正解SQLの実行結果と突き合わせて採点する構成で、検証を行います。

> - **動作確認** — 下記 [「セットアップと実行」](#セットアップと実行) を参照。`--dry-run` は LLM を呼ばないため、APIキーが無くても動かせる。
> - **開発の全体像** — 開発サイドの第一文書は [`docs/Concept_and_Overview.md`](docs/Concept_and_Overview.md) とし、要件抽出や開発計画のほか、設計判断とその経緯を記録している。

---

## 背景

以前に RAG実験の支援ツールを作り、実験をしながら次の点を疑問に思っていた。  
**企業が AI を実務に活用しようとするとき、RAG から入るのが最短なのか。**

RAG は重要な切り口ではある。  
ただし労力の多くは **「人の言語をいかに解釈し、欲しい答えへ辿り着かせるか」**——際限のない入力の揺れ——に向かう。toC 対応業務では確かにそれ自体、大きな価値があるが、企業によっては必ずしも最優先ではない。

また一方でも我々エンジニアは、人の言葉より遥かに効率の良い言語——プログラミング言語や SQL——をそもそも扱ってきて、**企業には、そちら側の有益なデータソースも山のようにある。**  

そこで、**もっと先に手をつけるべき、費用対効果の高い切り口**があるのではという観点で、開発と実験を試みた。

---

## 目標の設定

企業のデータソースの内、経営に最も直結し再利用されるものとして**売上データ**が浮かぶ。
そこに RAG で実現している「会話で相談する」要素を掛け合わせ、**「売上戦略を相談できるシステム」** をテーマに据えた。

売上データは通常DBに存在するため、**自然言語の問いを SQL に変換して実行する部分**が要る。
本リポジトリではまず、それを検証することにした。

### 入口の基軸（最も重視する方針）

しかし入口は、**利用者の自由な問いを AI が解釈する形にはしない。**

> **売上の分析に関する技術や情報もまた、十分に蓄積され体系化されたリソース** であり、  
> 相談すべきはそれに長けた専門家である。そんな専門家を相談相手に想定した場合、  
> **会話の出発点は自由ではなく補正されて然るべき。**

専門家は **企業から売上分析を相談される場面** で、相談者の言葉に対して **ゼロベースで回答を推論** したりはしない。先に **現存するデータを精査し、基本的な分析を済ませてから席に着くはずで、**  
**DBの構造・収容範囲・目的に沿って見るべきもの・現存データでは答えが出ないこと** など、  
利用者が問いを立てる**前に、既知の事実として提示し共有する** ものであり、  
ゼロからの問いを受けて **自由文を解釈する力に頼る** ことは筋が悪い、と容易に想像できる。

そして推論開発のリソースはむしろ、  
**専門家の準備（既存のデータ × 専門家の知見 ⇒ 事前案内）の自動化** や、  
**専門家の洗練された言葉を、より分かりやすく嚙み砕く作業** に注がれるべきと考える。


### 開発の土台（評価基盤とデモDB）

入口の基軸に掲げた事前案内も、突き詰めれば DB への集計 ——SQL—— の上に成り立つ。  
つまり、**この系のすべてが SQL の上に載る** ことになる。

ここで注意すべきは **「構造化データは静かに間違う」** という教訓であり、
SQL は集計を取り違えてもエラーを出さず、**それらしい数値が返る** ため、
誤りは出力を眺めても分からず、**正解と突き合わせて初めて分かる。**
従って土台には、**生成された SQL の正しさを測れる仕組み**を置いた。

その仕組みには、直前に作っていた RAG の実験管理ツール（実験を記録して比較する仕組み）が有効と考え、土台として流用する開発方針を取った。
パラメータを変えて測り、比べられることが重要で、**SQL を生成できることがゴールではない。**

データソースには、架空の小売チェーンのデモDB `demo_sales` を自作（40店舗・会員20,000人・売上明細198,491件）。  
現実のデータで起こりがちな **7つの落とし穴（表記ゆれ・欠損・論理削除・粒度違いなどデータエンジニアリングの一般的な癖）** を意図的に仕込んだ。

## ロードマップと現在地

開発は次の順序で進めている。

| # | 内容 | 現状 | 開発フェーズ |
|---|---|---|---|
| 1 | 答えの正しさを測る土台を作る（評価基盤）。何を比べても数字が濁らない状態（→ 結果1） | 完了 | 段階1 |
| 2 | 専門知識ベースを明文化する（データプロファイリングと診断フレームワーク） | 完了。成果物は [`sample/sales/`](sample/sales/) に公開 | 段階1.5 |
| 3 | 判定を、自由文の解釈から #2 のルールへ寄せる（→ 結果2） | 完了 | 段階2 |
| 4 | 利用者が問う前に、DBの構造・収容範囲・答えの出ない範囲を案内する（「入口の基軸」の実装） | 設計中 | 段階1.5 |
| 5 | このデータから戦略的な洞察を引き出す | 未着手 | 段階3・4 |

* 「開発フェーズ」欄とは
  * 当初からの積み上げ設計（段階1: 正しさの保証 → 段階1.5: 専門知識ベースと事前案内 → 段階2: 曖昧さの判定 → 段階3・4: 分解と可視化）に由来する内部の呼称で、`docs/` の設計文書と対応する。
  * 段階1.5 は明文化（#2）と案内（#4）に分かれ、前者だけが完了しているため2行にまたがっている。

* #5 は題材を別途計画中  
  現状の7つの落とし穴は自作したもので、戦略分析固有の知見でも発見でもないため、別途題材を足して測る必要がある。

* 背景に挙げた疑問 ——RAG から入るのが最短なのか—— の検証方法  
  比較実験で白黒がつく類のものではなく、目安としては、素人質問の揺れを吸収する作業に追われず、事前案内と分析の設計に資源を注ぐことで、 **#5の設計や検証がどれだけ建設的でスムーズに行えるか —— その手応え** が判断材料になると考えている。

## 結果

ロードマップ #1・#3 で得た測定を示す。  
* 結果1 は、35問の「業務質問 → 正解SQL」の対（以下 **評価データ**）に対してパイプラインを走らせ、生成SQL の実行結果を正解SQL の実行結果と突き合わせた**一致率**で行っている。  
* 結果2 は SQL を生成しないため、この評価データではなく、**判定の正しさを確かめるために別途作った質問セット**を用いる。

### 1. 評価データの修正だけで 0.4286 → 0.8857（ロードマップ #1）

初版の評価データには曖昧さや採点側のバグがあり、一致率は 0.4286 から始まった。  
**そこからモデルもプロンプトも変えず、評価データ側の不備を直すだけで 0.8857 まで上がった。**

| 段階 | 一致率 | 何を直したか |
|---|---|---|
| 初版 | 0.4286 | — |
| 順序判定の是正 | 0.4286 | 評価側のバグ（正解SQLの `ORDER BY` から順序要求を推測していた） |
| 3観点の曖昧さ解消 | 0.6857 | ラベル文字列 / 丸め桁数 / 集計定義 |
| 4観点目の解消 | **0.8857（31/35）** | 出力する列 / 相対期間の境界 |

同じ期間に、モデルを上位のものへ差し替える実験も行った。

| 手 | 結果 |
|---|---|
| 列の意味説明をスキーマに与える（`schema_desc: comment`） | **+0.1714** |
| モデルを上げる（`gpt-4.1-mini` → `gpt-4.1`） | **±0.0000**（正解していた31問が完全一致）。コスト約5倍 |
| `self_correct` | ±0、トークン +3.8% |
| `few_shot: 3` | 一致率は誤差の範囲、**実行成功率 → 1.0** |

> **説明を与える効果（+0.09〜0.17）が、モデルを上げる効果（±0）を上回った。**

ここで分かったのは、**測定対象（評価データ）の質が悪いと、モデルやプロンプトの比較そのものが成立しない**ということである。  
詳細は [`docs/MEASUREMENT.md`](docs/MEASUREMENT.md)。

### 2. LLM の総合判断による曖昧さ判定は、誤検出率 0.667 で頭打ち（ロードマップ #3）

原因は、**質問文にもデータにも無い軸**（活動実績のない店舗、休業中、発売開始前の商品など）を  
LLM がその都度作り出していたこと。プロンプトの言い回しでは解消しなかった。

工程を3つに分け、判定だけを決定論に置き換えた。

| 工程 | 担当 |
|---|---|
| ① 自然文 → 構造化 | **AI** |
| ② 応答文言の生成 | **AI** |
| ③ 曖昧さの判定 | **ルール** |

コードによる再現可能な採点で、**113件の診断セット**（判定の回帰を潰すために蓄積した質問）に対し **53〜56% → 75〜76% → 80〜84%**。

**AI を信用していないから③をルールにしたのではない。  
測った結果、そこは AI の仕事ではないと分かったからである。**  
設計は [`docs/AD_Stage2_RuleDesign.md`](docs/AD_Stage2_RuleDesign.md)。

## 測定の制約

上記の数字には次の制約がある。

- **測定は、途中で優先度を組み替えながら進めた。** 当初は精度の改善と自由文の揺れの吸収に比重が寄り、工数が想定を超えた。上記の数字は、その過程で出た測定と、組み替え後の測定の両方を含む。
- **盲検検証は未実施。** 10本目の質問セットは24件中16件（67%）が既存と重複し、盲検として成立しない。重複率は 4% → 17% → 18% → 67% と加速した。**このデモDBに対する自然な業務質問が尽きた。**
- **主指標にあたる型（実績の無い実体を並べるか）が、量として測れていない。** 5セット113件で延べ8件（7%）。原因はデモDBの作りで、この型が成立するには「実績ゼロの実体が実在する」ことが要るが、商品も日も月も0件である。
- **単一のデモDB・単一のモデル系列でしか測っていない。** 検証は2026年8月時点。
- **DB そのものの版を記録する仕組みが無い。** 評価データの版とプロンプトの版は記録しているが、DBを再生成すると過去の実験が再現不能になる。
- **本番運用の観点（レイテンシ、クエリあたりコスト、同時実行、監査ログ）は範囲外。**

数字は幅で書いている。**同一コード・同一データ・`temperature=0.0` でも値は動くため**で、  
その実測と作法は [`docs/MEASUREMENT.md`](docs/MEASUREMENT.md) 2節にある。

## 生成SQLの扱い

通常は、開発者が書いて検証もする SQL を **LLM が生成し、人が事前に確認しないで実行** する以上、破壊的な文（`DROP` / `UPDATE` / `DELETE`）・対象外スキーマへの参照・巨大なスキャンへの対策が必須となる。  

これらを次の3層で実現する。

| 層 | 担当 | 効くもの |
|---|---|---|
| 1 | `sql_validator` | 構文の静的検査、参照先のホワイトリスト、`LIMIT` 付与 |
| 2 | `sql_executor` | `SET TRANSACTION READ ONLY`、`statement_timeout` |
| 3 | DBロール | `demo_sales` の `SELECT` のみを持つ専用ロール |

* **1層目と3層目が無くても2層目だけで書き込みは止まる**、という重ね方にしてある。  
* 1層目は正規表現ベースで本物のパーサではないため、**この層だけで安全と見なさない。**  
* 2層目単独の効きと、3層目の拒否は、それぞれ実測して記録してある（[`sample/sales/README.md`](sample/sales/README.md)）。


## セットアップと実行

テストは外部APIもベクタ索引も要らない（`FakeLLMClient` と依存性注入）。PostgreSQL のみ必要。

```bash
cp .env.example .env          # DB接続情報を設定
pip install -r requirements-dev.txt
python manage.py migrate
python manage.py test app     # 675 tests
ruff check .
```

実験を走らせる。**`--dry-run` は LLM を呼ばないので、APIキーが無くても確認できる。**

```bash
python manage.py run_nl2sql_experiment --dry-run
python manage.py run_stage2_rule_experiment --dry-run
```

本実行には `OPENAI_API_KEY` と課金が必要（評価データ35問に対してLLMを呼ぶ）。

```bash
python manage.py run_nl2sql_experiment --name baseline --schema-desc comment
python manage.py runserver     # http://localhost:8000/nl2sql/ で結果を閲覧
```

デモDBの構築手順は [`sample/sales/README.md`](sample/sales/README.md)。

**技術スタック**: Python 3.12 / Django 5.1 / PostgreSQL / OpenAI API

## 実施体制

実装とドキュメントの起草には Claude Code を用い、役割を分けた複数セッションで進めた。  
**設計方針の決定・スコープの確定・打ち切りの判断は筆者が行っている。**

該当する判断は次の3つで、いずれも経緯を [`docs/Concept_and_Overview.md`](docs/Concept_and_Overview.md) に記録してある。

- **問いを受けてから自由文を推論する設計をやめ、入力前に案内する形へ変えた**（3節・6節）
- **目標水準を「専門家の再現（10）」ではなく「利用者を4〜5へ引き上げる誘導」と定めた**（4節）
- **段階2への追加投資を、盲検の台が枯渇した時点で打ち切った**（9節）

コミット履歴は公開用に作り直しているため、開発時の履歴とは対応しない。
