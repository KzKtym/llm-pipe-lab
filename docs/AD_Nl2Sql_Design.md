# 設計書: NL→SQL パイプラインと評価基盤

最終更新: 2026-08-18 / 対象: `app/nl2sql/`

引き継ぎと作り直しに耐えることを目的に、**なぜそうしたか**を残す。
何をしたかはコードと `appendix/` の測定記録にある。

---

## 1. 目的とスコープ

日本語の質問から SQL を生成し、実行し、**正しさを数値で測る。**
パラメータを変えて測り、比べられることが目的で、SQLを生成できること自体は手段。

対象外: チャットUI、複数ターンの対話、SQL以外の出力、PostgreSQL 以外の方言。

---

## 2. 全体の流れ

```
評価データ(35問)
   │
   ├─ 質問 ──┐
   │         ▼
   │   [generator] ── プロンプト組み立て → LLM → SQL抽出
   │         │
   │         ▼
   │   [sql_validator] ── 構文検査・ホワイトリスト・LIMIT付与
   │         │
   │         ▼
   │   [sql_executor] ── 読み取り専用トランザクションで実行
   │         │
   │         ▼（失敗なら error を戻して再生成: pipeline）
   │      実行結果
   │         │
   └─ 正解SQL ─┴─▶ [result_compare] ── 一致判定
                          │
                          ▼
                    [evaluator] ── 集計（一致率・タグ別・エラー種別）
                          │
                          ▼
                    [services] ── Nl2SqlExperiment に保存 / 明細をファイルへ
```

### モジュールの責務

| モジュール | 責務 | 依存 |
|---|---|---|
| `app/common/llm_client.py` | LLMプロバイダの抽象化 | — |
| `core/schema_introspector.py` | スキーマ取得と説明テキスト化 | — |
| `core/generator.py` | プロンプト組み立て・SQL抽出 | llm_client |
| `core/sql_validator.py` | 実行前の静的検査 | — |
| `core/sql_executor.py` | 読み取り専用実行・エラー分類 | validator |
| `core/result_compare.py` | 実行結果の突き合わせ | validator |
| `core/pipeline.py` | 生成→検査→実行→再試行の組み立て | generator, executor |
| `core/evaluator.py` | 一括実行と集計 | pipeline, result_compare |
| `params.py` | 実験パラメータの正規化・検証 | — |
| `services.py` | 実験1回分の組み立てと記録 | 上記すべて, models, store |
| `store.py` | 明細のファイル入出力 | — |
| `web/` | 画面（閲覧のみ） | services 経由 |

**依存の向きは `views → services → core / store` の一方向。**
ビューから `core/` を直接呼ばない。移植元の RAG 実験ツールと同じ約束。

## 3. 効いている設計判断

### 3.1 生成SQLは3層で守る

| 層 | 担当 | 効くもの |
|---|---|---|
| 1 | `sql_validator` | 構文の静的検査、参照先のホワイトリスト、LIMIT付与 |
| 2 | `sql_executor` | `SET TRANSACTION READ ONLY`、`statement_timeout` |
| 3 | DBロール `demo_readonly` | `demo_sales` の SELECT のみ |

**1層目と3層目が無くても2層目だけで書き込みが止まる**、という重ね方にした。
検査は正規表現ベースで本物のパーサではないため、**この層だけで安全と見なさない。**

2層目単独の効きはテストで固定してある（書き込み権限のある接続で
INSERT/UPDATE/CREATE を試し、すべて `read_only` で拒否されることを確認）。

`search_path` を対象スキーマだけに絞ってあるので、修飾なしの表名が
`public` へ流れ込む経路も塞いである。

### 3.2 再試行の判断はパイプラインだけが持つ

生成・検査・実行の各層は互いを知らない。どう並べ何回やり直すかを決めるのは
`Nl2SqlPipeline` だけ。`self_correct` と `retry_k` を実験パラメータとして
振るために、判断を1箇所へ閉じた。

**検査で落ちた場合も書き直しの対象**にする。「禁止されたキーワードを含みます」も
モデルには十分な手がかりで、実行時エラーと区別する理由がない。

### 3.3 LLMの失敗を2種類に分ける

| 例外 | 意味 | 扱い |
|---|---|---|
| `LLMFatalError` | 認証切れ・レート超過 | **ループごと中断** |
| `LLMTransientError` | 通信断・単発の不備 | その1問の失敗として次へ |

数十件をループで回すため、この区別が無いと認証エラーで全件叩き続ける。

### 3.4 未実装のパラメータを指定されたら落とす

`schema_mode: retrieved` と `value_hint` は未実装で、指定すると
`UnsupportedParameter` を投げる。

黙って無視すると**記録に残るパラメータと実際に走った処理が食い違う。**
後から実験一覧を見て「この設定で測ったはず」という前提が崩れると、
比較そのものが信用できなくなる。静かにずれるより落ちるほうがよい。

### 3.5 評価データの版を記録する

`Nl2SqlExperiment.dataset_digest`。**版が違う実験のスコアは比較できない。**
同じ `schema_desc: comment` でも、評価データの版によって 0.4286 と 0.8857 になる。

ダイジェストは**読み込んだ内容から作る**（ファイルのバイト列ではない）。
対象は `id` / `question` / `gold_sql` / `ordered` / `tags`。`note` は含まない
（採点に効かないため）。整形の手直しで版が変わらないようにしてある。

### 3.6 集計はDB、明細はファイル

1問ごとの生成SQL・エラー・判定理由は行数が多く、DBの列に入れると一覧の
取り回しが悪い。`data/nl2sql/logs/exp_{id}.json` に出す。移植元の RAG 実験ツールと同じ扱い。

`data/` は Git 管理外。**保存先は `settings.NL2SQL_LOGS_DIR` で上書きできる。
テストは必ず上書きすること**（テストDBの id で実ファイルを書き潰した事故がある）。

## 4. 評価の考え方

### 4.1 主指標は実行結果一致率

同じ答えを出す SQL の書き方は無数にあるため、文字列比較はしない。
**実際に実行した結果**で比べる。

| 指標 | 定義 |
|---|---|
| 実行結果一致率 | 正解SQLと生成SQLの実行結果が一致した割合（**主指標**） |
| 実行成功率 | 生成SQLがエラーなく実行できた割合 |

### 4.2 順序を見るかは評価データが明示する

`EvalQuestion.ordered`。**既定は「見ない」。**

正解SQLの `ORDER BY` から推測してはいけない。「支払方法ごとの取引件数は？」の
ような順序を問わない質問でも、正解SQLには見やすさのために `ORDER BY` が
書かれることが多く、それを根拠にすると**正しい答えを不正解と判定する**。
実際にこの誤りで5問（14ポイント）落としていた。

### 4.3 値のならし

| 対象 | 扱い |
|---|---|
| 数値 | `Decimal` に寄せて6桁で丸める（`1200` と `1200.00` と `1200.0` を同じに） |
| 真偽値 | **文字列 `"true"`/`"false"` に逃がす**（Python では `True == Decimal(1)` になるため） |
| 日付・時刻 | ISO文字列 |
| 文字列 | 末尾の空白のみ落とす（`char(n)` のパディング対策） |
| NULL | `None` のまま。`0` や空文字とは一致しない |

列名は比較しない（`count(*)` と `count(*) AS cnt` は同じ答え）。

### 4.4 正解SQLが流せない問題は分母から外す

評価データの不備であってモデルの責任ではない。`gold_failed` として件数だけ残す。
**この件数が0でなければ評価データを直すべき**というサイン。

### 4.5 タグ別の内訳を必ず出す

全体の正答率が 0.62 と分かっても次の手は決まらないが、
「`表記ゆれ` が 0.2、`集計` が 0.9」と分かれば決まる。

## 5. 評価データの品質基準（重要）

**このプロジェクトで最も学びが大きかった部分。**
スコアの 0.4286 → 0.8857 は、すべて評価データの修正で起きた。

質問は**答えを一意に決めなければならない。** 5つの観点がある。

| # | 観点 | 悪い例 → 良い例 |
|---|---|---|
| 1 | 表示用ラベル | 正解SQLが `'非会員'` を発明 → 質問文にラベルを明記 |
| 2 | 丸め桁数 | 「何％？」 → 「小数第1位まで」 |
| 3 | 集計の定義 | 「売上」「割合」が2通りに読める → 質問文で確定 |
| 4 | 出力する列 | 「店舗別」 → 「店舗名ごと」。列数も明示 |
| 5 | 対象の母集合 | 「閉店した店舗」に売上ゼロの店を含めるか（**未解消。確定基準では 25/35 = 71%。8節**） |

**`note` に書いても効かない。** `note` は人間向けの覚え書きで、
プロンプトには渡していない。モデルに伝えたいことは質問文に書く。

### 評価データを直すときの原則

- **落ちた問題だけを直さない。** 現在のモデルの挙動に合わせて評価データを
  歪める行為で、次にパラメータを変えれば同じことが起きる。全問を同じ基準で見る
- **モデルに有利にするのが目的ではない。** 答えが一つに定まる問題にすることが
  目的であり、結果としてスコアが下がっても構わない

## 6. 分析の型（3回同じ失敗をした）

| 回 | 誤り |
|---|---|
| 1回目 | 正解SQLの `ORDER BY` から順序判定を推測していた |
| 2回目 | タグ別の数字だけを見て「コメントが読まれていない」と断定した |
| 3回目 | （回避）中身を見るまで結論を出さなかった |

**数字が動かないときは、まず個別の生成SQLと正解SQLを並べる。**
タグ別の集計は「どこを見に行くか」を決めるための道具であって、
結論を出すための材料ではない。

実際、2回目に「モデルが落とし穴を外している」と結論づけた問題は、
中身を見ると**落とし穴は正しく処理しており、ラベル文字列と丸め桁数で
落ちていた。**

## 7. 実験パラメータ

| パラメータ | 値 | 状態 |
|---|---|---|
| `schema_desc` | `comment` / `hint` / `none` | 実装済み |
| `schema_mode` | `full` / `retrieved` | `retrieved` 未実装 |
| `value_hint` | bool | 未実装 |
| `few_shot` | 件数 | 実装済み（例示ファイルが未作成） |

| `model` / `temperature` / `max_tokens` | — | 実装済み |
| `reference_date` | ISO日付 | **評価時は必ず固定する** |
| `max_rows` / `timeout_ms` | — | 実装済み |

**few-shot の例示を評価データから取ってはいけない。** 測る対象に答えを

ファイルが無ければエラーにしてある。

## 8. 既知の限界

| 箇所 | 内容 |
|---|---|
| SQL検査 | 正規表現ベースでパーサではない。DBロールが最終防衛線 |
| `truncated` | 「切れたかもしれない」以上のことは言えない |
| 結果の型 | DBの型のまま返す。正規化は `result_compare` が担う |
| 方言 | PostgreSQL のみ。`dialect` はプロンプトの文字列としてのみ存在 |
| 評価データ | 母集合の曖昧さが **25/35** 残っている（当初 2/35 と見積もっていた。下記） |
| 質問文の一意性 | **質問文単独では一意でない問題がある**（下記） |

### 質問文単独での一意性について

段階1の質問文は **`gold_sql` とセットで一意**であり、質問文だけでは一意でないものがある。

| 問題 | 質問文が決めていない点 |
|---|---|
| q022（都道府県別の会員数トップ10） | `members.pref` の値域20種に含まれる**「その他」**を入れるか（`gold_sql` は含める） |
| q009（会員の男女別の人数） | `members.gender` の**「その他」**と **`NULL`（30%）**の扱い（`gold_sql` が固定） |
| q031（最も売れた商品トップ10） | `products.product_name` に**同名6組・12商品**がある。束ねるか分けるか（`gold_sql` が `product_name` で固定） |

**同じ構造が3件出ている。** いずれも段階1では `gold_sql` が解釈を固定していたため
顕在化せず、段階2で質問文だけになった途端に露出した
（対照群を作ったときの `pref`、段階2の評価データを組んだときの `product_name`）。

### 「対象の母集合」で数えると 25/35

上の3件は個別の例だが、**観点5「対象の母集合」に絞って35問を確定基準で数え直したところ、
質問文単独で一意でないものが 25件あった。**

内訳（延べ）は、結合欠落6・**フラグ18**・同義値3。従来この案件は「母集合の曖昧さは 2/35 = 6%」と
見積もって打ち止めにしていたが、**数えていたのは結合欠落だけ**で、フラグ（`close_date` /
`is_discontinued` / `is_active`）と同義値（関西/近畿、EC/オンライン）は
**7つの落とし穴の #4・#1 として別立てに分類されており、母集合の曖昧さとして数えていなかった。**

**分類の枠が2つあり、同じ現象を別々に数えていた。**

### 段階1と製品では、測っているものが違う（重要）

`gold_sql` は**質問文に書いていないことは何もしない**という素直な変換であって、
業務的な既定を体現していない。型2（フラグ）に該当する設問7件を確認すると、
**すべてフラグ条件が無く「全件を含める」を採っている。**

一方、製品として妥当な既定は「現役のみ」である。同じ質問でも答えが変わる。

| 質問 | 段階1の正解（`gold_sql`） | 製品の既定 |
|---|---|---|
| 店舗は全部で何店舗ある？ | **40**（閉店3件を含む） | **37** |

> **段階1は「質問文への忠実さ」を測り、製品は「業務的な妥当さ」を返す。
> 測っているものが違う。**

**どちらかをバグと見なして揃えにいかないこと。** とくに `evaluation_questions.json` を
製品の既定に合わせて直すと、`dataset_digest` が変わり `exp_12` 以降が比較不能になる。
具体例と数値は `../sample/sales/population_labels.json` にある。

**段階2 は質問文単独での一意性を要求するため、基準が一段厳しい。**
段階2 の評価データで同じ列を題材にする場合は、質問文で値域を確定させること
（判定手順は `MEASUREMENT.md` 10節）。

**段階1側は直さない。** `evaluation_questions.json` を変えると `dataset_digest` が変わり、
exp_12 以降の比較がすべて失われる。`gold_sql` が解釈を固定しているため実害は無い。

### 段階2の型4は、`pref` と `gender` の2列しか見ていない

**構造的な検出範囲の限界であり、調整では直らない。**

工程①（`axis_extractor.py`）の出力契約で、`CATCHALL` が取りうる値は
`NONE` / `pref_RESOLVED` / `pref_UNRESOLVED` / `gender_RESOLVED` / `gender_UNRESOLVED`
の5つしかない。**包括値・欠測を持つ他の列は、そもそも列挙に存在しない。**

盲検で実際に外れた（`s221`）。

| | |
|---|---|
| 質問 | 会員の年代別の会員数を出してください。 |
| gold | `[2, 4]` |
| 判定 | `[2]`（型4を検出できない） |

**「年代」は `members.birth_date` から導く区分で、`birth_date` の NULL は 5,980件ある。**
年代を決められない会員を「不明」行として並べるか落とすかは未確定だが、
**その列が対象に入っていない。**

同じ型4でも `pref`（`s209`）と `gender`（`s210`）は正しく検出できている。
**個別の質問の誤りではなく、値域の設計そのものによる。**

**直すなら、派生区分（`birth_date` → 年代）と、包括値・NULL を持ちうる他の列を
`CATCHALL` の対象へ加える必要がある。** 出力契約が変わるため、
**変更後は未知データで測り直すこと**（`MEASUREMENT.md` 3節）。

### `GROUP_BY` はマスタ実体＋時間の2軸を同時に表現できない

**出力契約の構造的な限界であり、プロンプトの言い回しでは直らない。**

`GROUP_BY` は`MASTER_STORES` / `MASTER_MEMBERS` / `MASTER_PRODUCTS` / `TIME` /
`FACT_COLUMN` / `NONE`の**単一値**しか取れない。**「店舗ごとに、月別の」のように
マスタ実体の軸と時間の軸を同時に求める質問には、1つしか答えられない。**

盲検で実際に外れた（`s513`。以後の測定でも残存を確認）。

| | |
|---|---|
| 質問 | 店舗ごとに、2026年上半期の月別売上を出してください。 |
| gold | `[1, 2]`（ロスター完全性＝型1と、閉店店舗のフラグ＝型2の両方が未確定） |
| 判定 | `GROUP_BY: "MASTER_STORES / TIME"`（契約違反の2値同時出力。パーサは先頭の
  `MASTER_STORES`だけを拾う）。`FLAG_STORES`が`NONE`に落ちやすく、型2を検出できない |

**項目6（`FLAG_*`の「関わる」判定）に「他の軸が同時にあっても
マスタ実体側の関わりは消えない」を追記して直そうとしたが、先に
別に確立していた一般則（マスタ表の日付列由来の区分はTIME）を壊す相互作用が
見つかり、費用対効果で追記を取り下げた**（`s513`は0/5→1/5の改善に留まる一方、
既存の確認は6/6→ほぼ0/16まで崩れた）。

**取り下げた後も、元には戻っていない。** 項目6を戻した状態（現行）で
「店舗の開店年別に、店舗数の推移を教えてください。」を測り直すと、
**28回中5回（約18%）しか `TIME` にならない**（受け入れレビュー時の実測。
一般則を入れた時点では 6/6）。**その一般則は
「マスタ表の日付列由来なら `TIME`」ではなく、「実体を数える言い回しでは効かない」
という限定つきになっている。** 同じ規則でも「商品の発売年別に、新商品の登録点数を」は
12/12 で維持されており、**壊れているのは実体を数える形だけである。**

**プロンプトの言い回しをこれ以上重ねる
より、`GROUP_BY`が複数軸を同時表現できるよう出力契約自体を見直す方が
筋が良い可能性がある。** 出力契約が変わるため、**変更後は未知データで
測り直すこと**（`MEASUREMENT.md` 3節）。

## 9. 作り直すとしたら残すもの

優先度順。

1. **評価データの品質基準（5節）** … ここが最も高くつく学び
2. **3層防御（3.1）** … 導入検討の場で必ず聞かれる
3. **順序判定を評価データが明示する（4.2）** … 推測すると必ず誤る
4. **評価データの版の記録（3.5）** … 無いと過去の数字が意味を失う
5. **未実装パラメータで落とす（3.4）** … 記録と実態のずれを防ぐ
