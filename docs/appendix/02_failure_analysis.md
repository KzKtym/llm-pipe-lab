# 残った失敗の精査

- 日付: 2026-08-15
- 対象: exp_9（`schema_desc: comment`、一致率 0.6857）で落ちた問題の中身
- 前提: 前回の再測定で、説明の与え方では動かないタグが4つ残った

---

## 1. 目的

`サマリの欠落` 0/2、`期間_相対` 0/2、`並べ替え` 2/6、`上位N` 1/3 が
3条件（comment / hint / none）とも動かなかった。

**モデルの限界なのか、まだ評価データの問題なのかを、中身を見て判別する。**
過去に一度、数字だけを見て誤った結論を出しているので、同じ手順は踏まない。

---

## 2. 結論

**5件のうち4件は、モデルの誤りではなかった。**

| 問題 | 落ちた理由 | 責任の所在 |
|---|---|---|
| q011 | `store_name` と `store_id` の違いのみ | 評価データ |
| q016 | 同上 | 評価データ |
| q027 | 同上 | 評価データ |
| q031 | 出力列（2列と4列）＋ 期間の解釈差 | 評価データ |
| q028 | `store_id` が ambiguous で実行エラー | **モデル** |

---

## 3. 検証の方法

「識別列が違うだけ」という見立てを、思い込みで済ませずに確かめた。
正解SQLと生成SQLを両方実行し、**先頭の識別列を除いた残りを多重集合で比較**した。

```
q011: 行数 gold=37 gen=37 / 列 gold=[store_name, sales_amount] gen=[store_id, total_sales_amount]
      識別列を除いた値が一致: True
q016: 行数 gold=5  gen=5  / 列 gold=[store_name, txn_count]    gen=[store_id, total_transaction_count]
      識別列を除いた値が一致: True
q027: 行数 gold=38 gen=38 / 列 gold=[store_name, avg_daily_sales] gen=[store_id, avg_daily_sales]
      識別列を除いた値が一致: True
```

**数値は完全に一致している。** 集計もフィルタも正しく、店舗を名前で出すかIDで出すかだけが違う。

---

## 4. 新しく分かった曖昧さの型：出力する列

前回は3観点（ラベル文字列 / 丸め桁数 / 集計定義）を潰した。
**4つ目が残っていた。**

> 「店舗別の売上」と言われたとき、`store_name` を出すのか `store_id` を出すのか、
> 質問文からは決まらない。

生成SQLが `store_id` を選んだのには理由がある。3件とも
`daily_store_summary` から集計しており、`stores` と結合していない。
**結合しなければ店舗名は手に入らない。** 質問が名前を要求していない以上、
結合を省くのは無駄のない選択で、SQLとしてはむしろ素直である。

q031（トップ10商品）も同型で、正解が `product_name` + 数量の2列なのに対し、
生成は `product_id` / `product_code` / `product_name` / 数量の4列を返した。
**どの列を出すかを質問が決めていない。**

### これはモデルの問題か

「業務担当者が読む答えとしては店舗名が自然」という主張は成り立つ。
しかし**それは提示の良し悪しであって、SQLの正しさではない。**
提示の判断まで測りたいなら、質問文がそれを要求していなければならない。

現状は「測りたいもの（SQLの正しさ）」と「測っているもの（提示の一致）」がずれている。

---

## 5. 本物のモデルの誤り（1件）

### q028

```
column reference "store_id" is ambiguous
```

`stores s LEFT JOIN daily_store_summary dss` の後、`GROUP BY store_id` と
別名を付けずに書いたため、どちらの `store_id` か決まらない。**純粋なSQLの誤り。**

`ambiguous` は3条件とも1件ずつ出ており、エラー分類を追加しておいた効果が出た
（過去の測定で `other` から分離した）。

---

## 6. 影響の見積もり

exp_9 の不正解11件のうち、少なくとも4件が出力列の曖昧さによるもの。
**これを解消すると一致率は 0.6857 から 0.80 前後まで上がる**と見込まれる。

つまり現在のスコアは、まだ**評価データの曖昧さを2割弱ぶん含んでいる。**

---

## 7. 次にやること

1. **評価データの4観点目を潰す**（依頼書 `出力列の曖昧さ解消_OutputColumns` を作成し、
   データ担当へ依頼済み）
   - 出力する列を質問文で決める、または正解SQLを識別子基準に揃える
   - あわせて「直近3か月」のような相対期間の境界も一意にする
2. 潰した後にベースラインを測り直す（5回目）
3. **その後で** `self_correct` / `few_shot` の測定に入る

**パラメータを振るのは、評価データが安定してからにする。**
現状で振っても、動いたのがパラメータの効果か評価データの曖昧さかを判別できない。

---

## 8. 補足：この精査で分かった作業の型

同じ失敗を3回している。

| 回 | 誤り |
|---|---|
| 1回目 | 正解SQLの ORDER BY から順序判定を推測していた |
| 2回目 | タグ別の数字だけを見て「コメントが読まれていない」と断定した |
| 今回 | （回避）中身を見るまで結論を出さなかった |

**数字が動かないときは、まず個別の生成SQLと正解SQLを並べる。**
タグ別の集計は「どこを見に行くか」を決めるための道具であって、
結論を出すための材料ではない。
