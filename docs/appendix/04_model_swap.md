# モデルを上げても、データの癖は埋まらない

- 日付: 2026-08-16
- 対象: `gpt-4.1-mini` と `gpt-4.1` を、`schema_desc` の有無と組み合わせて比較
- 評価データ版: `ef3b87a5`（35問）

---

## 1. 問いの立て方

当初は「上位モデルにすれば一致率が上がるか」を測ろうとしていた。
コンセプト（`Concept_and_Overview.md`）を読み直して、問いを立て直した。

> このシステムの主張は「SQL を書けない人の代わりに書く」ではなく、
> **「SQL は書けても、そのデータの癖を知らない人が間違える箇所を、間違えずに書く」。**

この主張が正しいなら、次が言えるはずである。

> **モデルを賢くしても、データの癖は埋まらない。**

「賢いモデルを使えば済む話ですよね」は導入検討の場で必ず来る質問で、
そこに数字で答えられるかどうかがこの実験の価値になる。

そこで**2×2で測った**（モデル × 説明の有無）。

---

## 2. 結果

| モデル | schema_desc | 一致率 | 実行成功率 | 表記ゆれ | トークン | 実験 |
|---|---|---|---|---|---|---|
| gpt-4.1-mini | comment | 0.8857（31/35） | 0.9714 | 4/4 | 70,532 | exp_12 |
| gpt-4.1-mini | none | 0.7143（25/35） | 0.9714 | **0/4** | 27,821 | exp_14 |
| **gpt-4.1** | comment | **0.8857（31/35）** | **1.0000** | 4/4 | 70,405 | exp_20 |
| **gpt-4.1** | none | 0.8000（28/35） | 0.9429 | **1/4** | 27,604 | exp_18 |

### 差の大きさ

| 何を変えたか | 一致率の差 |
|---|---|
| モデルを上げる（comment 同士） | **±0.0000** |
| 説明を与える（gpt-4.1 同士） | +0.0857 |
| 説明を与える（mini 同士） | **+0.1714** |

**説明を与えることの効果が、モデルを上げることの効果を上回る。**
というより、モデルを上げる効果はゼロだった。

## 3. 正解した問題が1問も変わらなかった

同じ 31/35 でも中身が違う可能性があるので、問題単位で突き合わせた。

```
mini/comment(exp_12) vs 4.1/comment(exp_20)
  mini だけ正解: []
  4.1 だけ正解 : []
```

**31問が完全に一致。入れ替わりすら起きていない。**
「たまたま同点」ではなく、**同じ問題を解き、同じ問題で落ちている。**

---

## 4. q032 は両モデルとも同じ誤りを犯す

仕込み#6（粒度違い）を踏む問題。

```sql
-- gpt-4.1-mini
SELECT store_type, ROUND(SUM(dss.sales_amount) / NULLIF(SUM(s.floor_area), 0), 1) ...
FROM demo_sales.daily_store_summary dss JOIN ...

-- gpt-4.1
SELECT store_type, ROUND(SUM(sales_amount) / SUM(floor_area), 1) ...
FROM demo_sales.daily_store_summary dss JOIN ...
```

**日次サマリ（1店舗×N日）と結合したまま `SUM(floor_area)` を取っている。**
分母に売場面積が日数ぶん足し込まれる。gpt-4.1 のほうが簡潔に書いているが、
**踏んでいる罠は同じ。**

しかも**エラーは出ない。それらしい数字が返る。** 仕込みの狙いどおりの失敗であり、
コンセプトが言う「間違えてもエラーが出ない箇所」の実例になっている。

---

## 5. モデルの賢さで改善したもの

**実行成功率だけ**（0.9714 → 1.0）。`comment` 条件で実行エラーが消えた。

これは `few_shot` でも起きた改善と同じ性質のもの（`few_shot` の測定）。

| 誤りの種類 | 何で直るか |
|---|---|
| 形式的な誤り（参照できない列、曖昧な列名） | モデルを上げる / 例示を与える |
| **データの癖**（表記ゆれ・粒度違い・単価の二重持ち） | **説明を与える以外にない** |

`schema_desc: none` の `表記ゆれ` は mini 0/4、gpt-4.1 でも 1/4。
「`region` に『関西』と『近畿』が同義で混在する」は、**このDBを見た人しか知り得ない。**
どれだけ賢くても、書かれていないことは当てられない。

---

## 6. 結論

**「賢いモデルを使えば済む」は、この課題では成立しない。**

- 一致率はモデル差 0、説明の有無で 0.09〜0.17 動く
- 上位モデルは**同じ問題で、同じ理由で落ちる**
- 改善するのは実行成功率＝形式的な正しさだけ
- コストは約5倍（同じトークン数で単価が上がる）

**`gpt-4.1-mini` + `schema_desc: comment` を既定とする。** 変更しない。

この結果は、コンセプト（「データの癖を知らない人が間違える箇所を、間違えずに書く」）
そのものの裏付けになる。**この検証で最も説明に使える1枚。**

## 7. 運用上の発見：TPM 上限で中断した

最初の `gpt-4.1 / comment` は **10問目で中断**した（exp_19）。

```
OpenAI API error 429: Rate limit reached for gpt-4.1 ... on tokens per min (TPM): Limit 30000
```

`comment` は1問あたり約2,000トークン。35問を連続で流すと分あたり上限を超える。

**設計どおりに動いた。** 429 → `LLMFatalError` → 評価ランナーが `aborted` を立てて
中断し、部分結果と理由を残した（評価ランナーの設計）。黙って遅くなるより
中断して理由が残るほうがよい、という判断が実際に効いた形。

### 対応：`pause_sec` を追加

`evaluate()` と `run_experiment()` に間隔（秒）を渡せるようにした。
**採点結果に影響しないので実験パラメータにはしない。**
4.5秒間隔（約24,000トークン/分）で35問を流しきれた（所要 184秒）。

### 積み残し：429 の分類は再考の余地がある

`llm_client` は 429 を `LLMFatalError`（中断すべき）に分類している。
しかし 429 には2種類ある。

| 種類 | 性質 |
|---|---|
| 課金枠の枯渇 | 待っても直らない → Fatal で正しい |
| **分あたり上限（TPM）** | **待てば直る** → 本来は待って再試行できる |

現状は両方 Fatal。**間隔を空ける運用で回避できているので急がない**が、
自動で待つようにするなら分類を分ける必要がある。

## 8. 次にやること

段階1（1問の答えが正しいことを保証する）で試せる手は、これでひととおり尽きた。

| 手 | 結果 |
|---|---|
| `schema_desc` | **効く**（0.71 → 0.89） |
| `self_correct` | 効果なし |
| `few_shot` | 一致率は誤差、実行成功率は改善 |
| **モデルの差し替え** | **効果なし** |

残る4件（q028・q030・q032・q035）のうち、2件は「対象の母集合」の曖昧さで、
**段階2（曖昧な質問を検出して聞き返す）の材料**として残すと決めている。

したがって次は**段階2への着手**か、**Phase 1-e（グラフ表示）**のどちらか。
段階2は「答えを出さずに聞き返す」判断を入れることになり、
評価の枠組み自体（一致率で測る）を拡張する必要がある。
