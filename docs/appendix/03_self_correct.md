- 対象: `self_correct: true` / `retry_k: 1`
- 基準: exp_12（`comment` / 0.8857 / 評価データ版 `ef3b87a5`）

## 2. 再試行は正しく走っている

実装が動いていないわけではない。

```
再試行が走った問題: [('q030', 2)]
判定が変わった問題: []
```

対象は1件で、2回目まで実行された。トークンの増分 2,682 も
プロンプト1本ぶん（約2,000）＋生成に相当し、辻褄が合う。

### q030 は同じ誤りを繰り返した

```
1回目: column "age" does not exist
2回目: column "age" does not exist   ← エラー文を返しても同じ構造で書き直した
```

質問は「会員を年代で区分し、各年代の売上構成比は？」。
モデルは `CASE WHEN age BETWEEN 20 AND 29 THEN '20代' ...` と書くが、
`age` はその位置で参照できない（副問い合わせで先に計算する必要がある）。

**エラー文は症状を伝えるが、直し方は伝えない。** 「`age` が無い」と言われて
モデルが選んだのは、`age` を定義することではなく、同じ構造での書き直しだった。

---

## 3. この測定の検証力は低い

**そもそも救う余地が1件しかなかった。** ベースラインの実行成功率は 0.9714 で、
実行エラーは q030 のみ。`self_correct` は実行エラーを対象にする仕組みなので、
**上限が +1問（+0.029）しかない条件で測っている。**

したがって「self_correct は効かない」と一般化はできない。言えるのは次まで。

> 評価データ `ef3b87a5` と `gpt-4.1-mini` の組み合わせでは、
> **有効にする理由がない**（コスト +3.8%、効果 0）。

効果が見えるのは、実行エラーがもっと出る条件（弱いモデル、方言の違うDB、
スキーマがもっと大きい場合）。**その条件になったら再測定する価値がある。**

---

## 4. 判断

**既定は `self_correct: false` のままとする。**

`retry_k` を増やす実験もしない。同じ構造を繰り返している以上、
回数を増やしても同じ結果になる公算が高く、トークンだけが増える。

---

## 5. 次にやること

残る失敗4件のうち、モデル側の誤りは2件。

| 問題 | 内容 |
|---|---|
| q030 | `age` を定義せず参照（**self_correct で救えなかった**） |
| q032 | 日次サマリと結合したまま `SUM(floor_area)` … 分母に面積を日数ぶん二重計上 |

どちらも**エラーを返して直る種類ではなく、書き方の組み立てそのものの問題。**
効きそうなのは次の2つ。

1. **`few_shot`** … 副問い合わせで中間値を作る書き方を例示で教える。
   q030 に直接効く可能性がある。`few_shot_examples.json` の作成が先
2. **モデルの差し替え** … q032 の二重計上は、集計SQLの定番の落とし穴。
   上位モデルで取れるなら難度の問題だと分かる

**先に `few_shot` を試す。** 例示の作成コストはかかるが、
「どう教えれば直るか」はモデルを上げるより持ち帰れる知見になる。
