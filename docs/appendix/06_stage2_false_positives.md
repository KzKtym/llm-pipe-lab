## 背景

前回の測定で段階2のベースラインとゆらぎが揃った。4回通算の実数は次のとおり。

| | 判定数 |
|---|---|
| 見逃し | **1 / 16**（曖昧4問 × 4回） |
| 誤検出 | **23 / 24**（対照6問 × 4回。TN は `exp_1` の c006 ただ1つ） |

10問中8問は4回とも同じ判定で、**ゆらぎは小さい。したがって誤検出の高さは構造的**である。
`exp_1` 単独の誤検出率 0.8333 は楽観的な値で、通算は 0.958 になる。

FP になった6問の確認文言には共通の型がある。モデルは全問で
**「活動実績のない〇〇を含めるか」**を聞いており、これは曖昧群 s001〜s004 で
聞くべき軸とまったく同じ。

**分岐するかどうかを決めるのは「結合で行が消えるか」の一点**（前段の測定 の規約）。
c001・c003 は `stores` の、c004・c006 は `products` の単純カウントで、
c005・c008 は `sales` の期間合計と割合。**いずれも結合で行が消えない。**
s001〜s004 だけが消える。

**そして判断ステップにはスキーマを一切渡していない。** テーブル構造を知らなければ、
その集計が結合を伴うかは原理的に判定できない。**これが本件の仮説。**

## 目的

判断ステップにスキーマ説明を渡し、**見逃しを増やさずに誤検出を減らせるか**を測る。

---

## 依頼元が確定した事項

### a. `none`（DDL のみ）から測る

仮説に必要なのは**テーブルと FK の構造**であって、列の日本語説明ではない。
段階1で `comment` が効いたのは**生成**タスク（列の意味を知らないと正しい SQL が
書けない）だからで、**判断は別のタスク**。同じ結論を持ち込む根拠がない。

### b. 3条件を一度に振る。各条件2回

`none` / `hint` / `comment` を各2回、計6実験（`exp_5`〜`exp_10`）。
1回あたり約3,400トークン・14秒なので、6回でも数分で終わる。

**各2回にするのは、1回だけだとゆらぎと効果を区別できないため。**
前回の測定 のゆらぎ測定で、2問が4回中1回変動している。

### c. 採用の基準

> **見逃しを増やさずに誤検出を減らせた、最も軽い条件を採る。**
> 見逃しが増えるなら不採用（主指標だから）。同点なら軽いほう。

段階1で `hint` を「コスト優先なら」と位置づけたのと同じ形。

### d. `hint` の結果は割り引いて読む

`sample/sales/schema_hints.md` にこの1行がある。

> `daily_store_summary` には、取引が1件以上あった（日付, 店舗）の組しか行が無い。
> **取引ゼロの日は行そのものが存在しない**

**これは s001 の曖昧さの正体そのもの。** `hint` で誤検出が減っても
「構造を理解した」証拠にはならない。**仮説を検証できるのは `none`。**
測ること自体はよいが、結論の根拠にはしない。

### e. プロンプト文言は変えない

`schema_desc` 以外を変えると、何が効いたのか分からなくなる。
段階1と同じ **「先にパラメータ、後から文言」** の順序。

### f. モデルと温度も変えない

`openai:gpt-4.1-mini` / `temperature: 0.0` のまま。段階2は判断タスクなので
段階1の結論（モデル差 ±0）をそのまま持ち込めないが、
**スキーマと同時に振ると交絡する。** 試すならスキーマの後。

|---|---|
| c003「まだ閉店してない店」 | `stores.close_date` が NULL でない店舗は閉店済み |
| c008「非会員の取引」 | `sales.member_id` が NULL の行は非会員の取引（全体の約4割） |

**正すと、むしろ説明が付く。** `hint` が効いたのは、**質問文の口語（「まだ閉店してない」
「非会員」）を、スキーマ上の列に橋渡しする1行があった**から。効果は偶然ではない。

### `comment` が c008 で効かない理由も説明できる

`sales.member_id` の DDL コメントはこう書かれている。

```
会員ID（members.member_id への外部キー）。約4割が NULL＝非会員（ゲスト）取引。
会員分析の母数に注意
```

**末尾の「母数に注意」が、聞き返しを誘発している可能性が高い。**
`comment` 条件の c008 は2回とも「取引がない期間や店舗を含めるか」と母数を問い返している。

**生成のために書いたコメントが、判断では逆に働く。** これは段階1の資産を段階2へ
そのまま持ち込めない実例で、記録に残す価値がある。

## 残る4問（c001・c004・c005・c006）の正体

3条件6回すべてで FP のまま動かなかった4問は、確認文言が同じ型をしている。

| id | 質問文が確定させた語 | モデルが持ち出した軸 |
|---|---|---|
| c001 | 「今ある店だけで」 | **活動実績のない店舗** |
| c004 | 「廃番抜きで」 | **取引のない商品** |
| c005 | （期間を明示） | **取引のない店舗・廃番商品** |
| c006 | 「現役の（廃番じゃない）」 | **販売実績のない商品** |

**フラグ軸は受け入れている。** c004 は「廃番抜きで」を確定と認めたうえで、
別途「取引のない商品」を持ち出している。

**そして4問はいずれもマスタの単純カウントか期間合計で、結合で行が消えない。**
存在しない軸を発明していることになる。`comment` 条件で出た「休業中や開店準備中」
「発売開始前の商品」は、その極端な例（後者は `products.launch_date` の存在から
発想した可能性がある）。

**構造を渡してもこの癖は止まらなかった。** 止めるならプロンプトの文言で、
**「質問文が指定していない軸を持ち出さない」**を明示するしかない。

## 既定の判断：`hint` を採用する

事前に決めた基準——**見逃しを増やさずに誤検出を減らせた、最も軽い条件**——を当てる。

- 見逃しは4条件すべて0〜1/16で悪化なし
- 誤検出は `hint` が最小（8/12）
- `hint` は `comment` より軽い（+360 対 +1,219 トークン/問）

**したがって `hint` を段階2判断ステップの既定とする。** 機序も説明が付いており
（前節）、「ヒント文が答えを含んでいるだけ」という `d` 節の懸念には当たらない。
橋渡しした2行は**質問文が既に言っていることをスキーマ語へ翻訳した**もので、
実運用でも同じものが用意される種類の情報である（`Concept_and_Overview` 1節の
「意味定義層」そのもの）。

**ただし解決ではない。** 誤検出 0.667 は依然として高く、残る4問は構造でも
ヒントでも動かない。

## 次にやること

**パラメータは尽きた。次はプロンプトの文言。**

段階1と同じ順序（先にパラメータ、後から文言）を守ってきて、`schema_desc` で
動くところまで動かした。残る4問は文言でしか動かない見込みが立った。

次の測定で確かめる仮説は1つ。

> **「質問文が指定していない軸を持ち出さない」と明示すれば、
> マスタの単純カウントに対する誤検出（c001・c004・c005・c006）は減る。**

条件を1つ付ける。**文言の測定は `hint` 固定で行い、基準線は `exp_7`・`exp_8`
（誤検出 4/6）に置く。** 既定を変えた以上、`exp_1`〜`exp_6` とは比較できない。

見逃しが増えないことの確認が主指標であることも変わらない。**「聞き返すな」と
指示する方向の変更なので、見逃しが増えるリスクが構造的にある。**
