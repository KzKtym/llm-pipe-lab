# 工程①プロンプトの変更履歴

`app/nl2sql/core/axis_extractor.py` のプロンプトに、いつ何を入れ、何を見送ったかの記録。
**設計そのものは `AD_Stage2_RuleDesign.md`。こちらは経緯である。**

読まなくても実装は追える。残している理由は2つ。

- **同じ手を二度打たないため。** 見送った変更と、その理由（費用対効果、
  他の判定を壊す相互作用）が書いてある
- **プロンプトの変更が、狙っていない項目を巻き込むという性質の実例として。**
  この履歴自体が `MEASUREMENT.md` 8節の根拠になっている

数字は測定当時のもので、幅の扱いは `MEASUREMENT.md` 2節に従う。

**`cNNN` は開発時の作業単位の通し番号である。** 対応する記録は公開範囲に含まれない。
**時系列の順序と、どの変更が同じ回のものかを示すためだけに残してある。**
リンクではないので、追いかける先は無い。

`c013` 論点F の線引き。

    ① 自然文を構造化された対象に落とす … AI（ここ）
    ② 開示文・確認文言の言い回しを作る … AI（`ambiguity_judge.py` の `phrase_disclosure`）
    ③ その構造が実際に曖昧かどうかの判定 … ルール（`population_rules.py`）

**SQLは書かない。** 要るのは「何を集計しているか」「何で分けているか」という
軽い理解で足りる（`c013` 1.3）。判定（③）はここでは行わない。
質問文がすでに軸を確定させている場合は `RESOLVED`、確定させていなければ
`UNRESOLVED` を返す——この切り分け自体はテキストの読み取りであり、AIの仕事。

`c015`：`c014` の盲検測定で見つかった抽出側の穴（パターンD/E/F/G、
FK列のNULL判定をマスタ結合と誤認するC寄りの誤り）を一般則として直した。
個別の質問への特例は入れていない。あわせて `GROUP_BY_GRANULARITY` / `LIMITED` /
`PERIOD` の3項目を追加した（`population_rules.py` 側の判定に使う）。

`c016`：`c015` 後の測定で残った見逃し（`GROUP_BY_RESOLVED` の誤判定）を
一般則として直した。**同じマスタ表について「フラグ（状態）の軸」と「ロスター完全性の軸」は
独立しており、一方を解消する語がもう一方まで解消したとみなさない**——という規則を
`GROUP_BY_RESOLVED` の項目説明に明記した（フィールド数・出力契約の行数は変わらない）。

`c022`：`c021`（4本目の盲検測定）で残った型1の誤り2件（どちらも時間軸）を
一般則として直した。(1) `GROUP_BY_RESOLVED` の解消語が「〜も」のような含める向きの
目印しか挙げていなかったのを、実績の存在を条件にして無いものを除く「除く向き」の
語も解消語であると明記。(2) `GROUP_BY` の `TIME` の説明を、実績表の日付列に限らず、
マスタ表が持つ日付列（開店日・発売日 等）から導いた年・月・日の区分も同じくTIMEで
あると明記（「マスタ表の列だからMASTER_*」という誤読を防ぐ）。フィールド数・
出力契約の行数は変わらない。

`c024`：`c023`（5本目の盲検測定）で見つかった、5回とも同じ誤りを
出す2件を直した。(1) `CATCHALL` の「値域の一部を名指し→RESOLVED」規則が、
「都道府県別」のように**値そのものを含まない列名だけの言い回し**にも誤って
適用されていたのを、**値そのものが質問文に現れているときだけ**RESOLVEDにする
よう絞った。(2) `REGION_FILTER` を新設（設計レビュー承認済み、出力契約が
10行から11行に増える）。質問文が `stores.region` の値に絞り込んでいる場合、
その値を`population_rules.py`側の照会（`flagged_activity.py`）へ渡し、
絞り込み後の集合でフラグ付き実体の有無を確かめられるようにした
（`region`以外の列への一般化はしていない）。

`c026`：`c024`が項目6（`FLAG_STORES`等）を狙わずに壊していたのを直した
（`c025`の測定で発覚。`REGION_FILTER`を外すと再現しなくなることを引き直しで
確認済み）。項目6冒頭の「関わるかどうかはGROUP_BYの対象かどうかでは決まらない」
という二重否定寄りの文を、「AGGREGATIONの対象、GROUP_BYの軸（そのマスタ表の列で
グループ化・分類している場合を含む）」という直接的な言い方に書き直した。
`REGION_FILTER`（項目10）自体は変更していない。出力契約・フィールド数は変わらない。

`c027`：`c025`で「安定した誤り」として残った2件のうち、`s514`だけ
直った。項目2の`TIME`に、曜日別・時間帯別のように日付・時刻から導いていても
値の種類があらかじめ閉じている区分はTIMEではないと明記した（`c022`の
「年」と「年代」の区別と同じ構図。曜日だけの特例にしていない）。`s513`
（グループ化しているマスタ表を「関わらない」と読む誤り）は、項目6への追記で
一度は直そうとしたが、項目2・項目6の変更が組み合わさると`c022`の既存の
確認（マスタ表の日付列由来の区分がTIME）を壊す相互作用が見つかり
（2つの変更は単独でも軽く劣化させたが、組み合わさるとほぼ効かなくなった）、
費用対効果（`s513`は0/5→1/5の改善に留まる一方、既存の確認は6/6→0〜2/16まで
崩れた）から**項目6の追記は取り下げた**。`s513`は未解決のまま
（根本原因は`docs/AD_Nl2Sql_Design.md` 8節「既知の限界」に記録）。`s505`
（`region`のグループ化でのフラグ誤発火）はgoldの事実誤りと判明したため
対応していない。フィールド数・出力契約の行数は変わらない。

`c030`：`c029`で見つかった安定した誤り3件（`s605`・`s607`・`s620`）を
試みたが、**どちらも見送った。** (1) 項目7（`SYNONYM`）への追記は`s607`・`s620`
自体は直したが（14/14ずつ安定）、無関係なはずの`s617`・`s624`型（`店舗別`の
`FLAG_STORES`判定）を安定した状態（`c026`以来20/20）から不安定な状態
（`exp_46`〜`50`の実測で`UNRESOLVED` 3/5・`NONE` 2/5＝約60%）へ悪化させる
副作用が見つかった。(2) 項目2（`GROUP_BY`）への
追記は`s605`自体は直したが、`c026`の確認（`店舗形態別`等の`FLAG_STORES`
判定）を安定した状態から不安定な状態へ悪化させる副作用が、言い回し・挿入位置を
変えても再現した。**いずれも費用対効果の判断が必要で、設計レビュー・統括の
決定を仰ぐため、両方とも追記を見送った**（`c030`
参照）。`s605`・`s607`・`s620`は3件とも未解決のまま報告のみに留めている。
フィールド数・出力契約の行数は変わらない。

`c031`：実験記録にプロンプトの版（内容ハッシュ）を残す `prompt_digest()` を
追加した。`_PROMPT`の文言・出力契約は変えていない。

`c032`：`c024`・`c027`・`c030`で3度、①のプロンプトに
1項目足すたびに別の箇所（多くは`FLAG_*`）が壊れる現象が起きたことを受け、
実装せず設計メモとして検討した（`c032`）。事実整理・
仮説・選択肢・推奨（`FLAG_*`を独立抽出に切り出す）をまとめた。

`c033`：`c032`の推奨への反論1（`CATCHALL`が`FLAG_MEMBERS`も壊すか
未検証）を切り分けで検証した。`CATCHALL`（項目8）の文言を`c024`以前に戻すと
`FLAG_MEMBERS`の分布が変わることを確認（n=20、`NONE`80%→50%）——設計レビューが
事前に決めた読み方どおり、`c032`の選択肢2の採用が支持された。

`c034`：選択肢2を実装した。**`FLAG_STORES`/`FLAG_MEMBERS`/`FLAG_PRODUCTS`を
`_PROMPT`（本体、9項目）から切り離し、`_FLAG_PROMPT`という別のプロンプト・別の
LLM呼び出しにした。** `AxisExtractor.extract()`は本体を呼んでから、その
`AGGREGATION`/`GROUP_BY`/`GROUP_BY_GRANULARITY`を`_FLAG_PROMPT`に渡して2回目を呼ぶ
（食い違い防止のため、`GROUP_BY`が`MASTER_*`ならその表は必ず「関わる」と明記した）。
`AxisExtraction`のフィールド・値域は変えていない（`raw_response`/`prompt`は
2回分を`---`区切りで連結、トークン・所要時間は2回分を合算）。`prompt_digest()`は
本体（`_PROMPT`）用のまま、新たに`flag_prompt_digest()`（`_FLAG_PROMPT`用）を
追加した——2本のプロンプトの版をそれぞれ追える（列を2本に分ける形を選んだ。
理由は`c034`参照）。**「①の脆さが無くなった」わけ
ではない**——本体側の項目同士の相互作用（`c027`型）はこの変更では直らない
（設計レビューの明示的な指摘）。呼び出し回数は1問あたり1回から2回に増えるが、
実測（24問1回・`rule_validation_questions_7.json`）ではトークンは約+17%
（89,949→105,436）、所要時間はほぼ変化なし（69.6秒→70.3秒）——`c032`の
「ほぼ倍」という見積もりより実際の増加は小さかった。**実装の過程で新たな誤りを
1つ見つけて直した**——`GROUP_BY`が`MASTER_*`であるという事実（食い違い防止のため
`FLAG_*`側へ渡している）を、`FLAG_*`側が「フラグの扱いを明言している」ことと
取り違え、グループ化されているだけの質問（例:「店舗形態別の売上合計」）まで
`RESOLVED`にしてしまう副作用があった（本体・単一呼び出し時代には無かった、
分離したことで新たに生まれた誤り）。「関わる」ことと「明言している」ことは別、
という一文と具体例を`_FLAG_PROMPT`に追記して直した。**当初`stores`側でしか
確認せず、統括の指摘で`members`側（`s609`「会員ランク別の会員数」）に同じ
回帰が残っていることが発覚した**（`c032`・`c033`で自ら指摘した
選択バイアスを実装でも繰り返した）。例を`stores`・`members`・`products`の
3表に拡張し、3表とも「明言なし→`UNRESOLVED`」「明言あり→`RESOLVED`」が
n=20で揃うことを確認した。**ただし`s612`（「都道府県別の会員数を**多い順に**」）
だけは例外で、`FLAG_MEMBERS`が`RESOLVED`のまま直っていない**——狙い撃ちの
追記はせず、`s605`・`s607`・`s620`と同種の未解決の誤りとして報告に留めた
（詳細は`c034`「追加対応」節）。

`c035`〜`c036`：`c034`後、8本目の盲検セット・91件の全量掃き出しで、
`_FLAG_PROMPT`の欠陥が想定より広い3つの型に集約されると判明した——
(A) `GROUP_BY_GRANULARITY: IDENTITY`や`AGGREGATION: ENTITY`（実体そのものを選ぶ・
数える）でも`FLAG_*`が明言なしで`RESOLVED`に倒れる（`c026`以来の維持確認に
使ってきた`s617`・`s624`自身が巻き込まれていた）。(B) `GROUP_BY`がそのマスタ表を
指していない（`FACT_COLUMN`等）のに`FLAG_*`が独立に過検出する。(C) `pref`/`gender`
列でのグループ化で`FLAG_MEMBERS`を見逃す（`s612`の仮説「多い順にが引き金」は
`s512`により否定、正しくは「`CATCHALL`対象列でのグループ化」）。

`c037`：3つの型をまとめて一般則で直した。「関わる」と「明言している」の
区別を`IDENTITY`/`ENTITY`にも拡張（A）、「関わる」の成立条件を「そのマスタ表
自身の列を明示的に使っているときだけ」に絞り実績表自身の列だけの区分では
関わらないと明記（B）、`pref`/`gender`列も他の分類列と同じ扱いと明記（C）。
91件の突き合わせ（診断であり採点ではない）で型完全一致48〜51/91→68〜69/91に
改善、`s617`・`s624`は`UNRESOLVED`に復帰。**型Cは列名を言う言い回し
（「都道府県別」「性別ごと」）では効いたが、値そのものを名指しする言い回し
（「男女別」）には効かず、`s611`・`s708`は未解決のまま残る**——無理に3つ揃えて
「直った」とはしていない。詳細は`c037`。

`c028`：③（`population_rules.py`）が意図的に絞っていた「実績ゼロの実体が
実在するかのデータ照会」の適用範囲を広げるため、①に`RATE_DENOMINATOR`
（10行目→11項目目、`NONE`/`MASTER_STORES`/`MASTER_MEMBERS`/`MASTER_PRODUCTS`）を
追加した。「会員1人あたりの平均購入回数」のように、`GROUP_BY`がそのマスタ表を
指していなくても、平均・比率の分母がマスタ実体の個数になっている質問を判定する。
`GROUP_BY_RESOLVED`（項目5）の適用条件も「`GROUP_BY`が`MASTER_*`か`TIME`」から
「…または`RATE_DENOMINATOR`が`NONE`でない」に広げた（解消語の判定ロジック自体は
変更していない）。**`_FLAG_PROMPT`は一切変更していない**（`flag_prompt_digest`が
変更前後で同一であることを確認済み）。実装中、分母を明示しない「〜別の平均」
（例:「会員ランク別の平均購入金額」）や「1取引あたり」（実績の分母、マスタ実体
ではない）への誤爆を見つけ、項目文に「分母を明示する語がある場合だけ」「実績を
分母にする語は対象にしない」を追記して一般則として直した。113件の突き合わせ
（診断であり採点ではない）で確認したところ、狙った時間軸の型1過検出は
13〜14件→2〜3件に減った一方、**`s521`（「北海道エリアの店舗」）で無関係な
`SYNONYM`の過検出が新たに現れた**（`RATE_DENOMINATOR`追加前は`NONE`8/8、追加後は
`region_UNRESOLVED`9/10、切り分けて確認）——`c026`以来繰り返し見つかっている
①の脆さの再発であり、深追いせず報告に留めた。詳細は
`c028`。

出力契約は本体10行＋`FLAG_*`用3行。パースできない場合は `LLMTransientError` を送出する
（段階2これまでの失敗分類を流用し、新しい例外は作らない）。
"""
