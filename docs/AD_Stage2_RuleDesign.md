`population_rules.py` / `ambiguity_judge.py` / `flagged_activity.py` /
`rule_scoring.py` / `stage2_rule_evaluator.py`

## 1. 目的とスコープ

質問文だけでは集計対象の母集合が一つに決まらないとき、**その未確定な軸を検出し、
型ごとに「聞き返す」か「既定を当てて開示する」かを決める。**

**SQLは生成しない。** 実行もしない。要るのは「何を集計しているか」「何で分けているか」
という軽い理解だけで足りる。

対象外: SQL生成・実行・結果の突き合わせ（段階1の担当）、チャットUI、複数ターンの対話、
`demo_sales` 以外のスキーマ。

### 段階1との違い

| | 段階1 | 段階2 |
|---|---|---|
| 測るもの | 質問文への忠実さ（`gold_sql` と同じ結果か） | 質問文単独での一意性 |
| 正解の持ち方 | `question` + `gold_sql` のセット | `question` + `unique` / `types` |
| 主指標 | 実行結果一致率 | 型の完全一致（7節） |
| 記録 | `Nl2SqlExperiment` | `Nl2SqlStage2RuleExperiment` |

段階1の質問文は **`gold_sql` とセットで一意**であればよい。`gold_sql` が解釈を固定するため、
質問文自体の曖昧さは顕在化しない。**段階2は質問文だけを入力にするため、基準が一段厳しい。**
段階1で問題にならなかった同じ質問が、段階2では未確定になる
（具体例は `docs/AD_Nl2Sql_Design.md` 8節「質問文単独での一意性について」）。

**段階1の評価データを段階2の基準に合わせて直してはいけない。**
`dataset_digest` が変わり、過去の実験と比較できなくなる。測っているものが違う。

## 2. なぜルール判定にしたか

### 2.1 先に LLM の総合判断で測った

最初の実装（`ambiguity_judge.AmbiguityJudge`）は、質問文を LLM に渡して
「そのまま集計してよいか（`ANSWER`）／先に確認すべきか（`CLARIFY`）」を
一発で判断させる形だった。指標は見逃し率（主指標）＋誤検出率（併記）＋
確認文言のキーワード一致（第2軸・参考値）。

**測った結果、次の2点が出た。**

- 誤検出率が **0.667（8/12）** で頭打ちになった。プロンプトへスキーマ説明を
  足しても下がらなかった（[付録06](appendix/06_stage2_false_positives.md)）
- **同一のモデル・同一の温度（0.0）・同一の質問文で、反復すると判定が割れた**
  （同上。10問中8問は4回とも同じ判定で、揺れる問いは特定できた）

### 2.2 「AI を信用しない」ではなく「測った結果、そこは AI の仕事ではない」

2番目の事実が効いた。**判定が反復で割れるということは、判定を LLM に置いている限り、
受け入れ側が同じ入力から同じ結論を再現できない。** 曖昧さの判定は
「この質問文はこの型に当たる／当たらない」という決定論であるべきもので、
推論の余地を残す場所ではない。

一方、**テキストから構造を読み取ること（「何を集計しているか」「何で分けているか」）と、
判定結果を業務の言葉にすること**は、規則で書き下せない。ここは LLM の仕事として残す。

**線を引き直した結果が3工程の分割（3節）である。** LLM を減らすことが目的ではなく、
推論が要る所と決定論であるべき所を分けた結果、判定だけがルール側に来た。

### 2.3 旧版は消していない

`ambiguity_judge.py` の `AmbiguityJudge` / `parse_judgement` / `build_prompt` は
**そのまま凍結して残してある。** 基準線となった実験群のコード上の参照先が
無くなると、当時の数字が何を測ったものか分からなくなる。指標体系も別テーブルに
分けた（`Nl2SqlStage2Experiment` と `Nl2SqlStage2RuleExperiment`）。旧版は
「聞き返せたか」の混同行列、新版は「未確定な軸を型別に検出できたか」で、
**同じ軸では比較しない。**

## 3. 3工程の分割

```
質問文
  │
  ▼
[① axis_extractor.AxisExtractor.extract]  … AI（LLM 2回）
  │   本体プロンプト（10行）→ FLAG_* プロンプト（3行）
  ▼
AxisExtraction（構造。13項目）
  │
  ▼
[③ population_rules.classify]  … ルール（LLMを呼ばない）
  │   └── flagged_activity の3関数（実データ照会）
  ▼
RuleResult（型1〜4の軸。resolved / default）
  │
  ▼
[② ambiguity_judge.phrase_disclosure]  … AI（LLM 1回）
  ▼
開示文
```

| 工程 | 担当 | 入力 | 出力 | 責務 |
|---|---|---|---|---|
| ① 構造化 | **AI** | 質問文 | `AxisExtraction` | 何を集計し何で分けているか、質問文が各軸を確定させているかを読む。**判定はしない** |
| ③ 判定 | **ルール** | `AxisExtraction`（＋実データ照会） | `RuleResult` | その構造が実際に曖昧かを型別に決める。**LLMを呼ばない** |
| ② 文言生成 | **AI** | 質問文＋`RuleResult` | 開示文 | 判定結果をどう言うかだけを決める。**新しい判断はしない** |

**番号は工程の順序ではなく役割の識別子で、実行順は ①→③→② である。**
③ が先に済んでいないと ② に渡すものが無い。

### 依存の向き

`stage2_rule_services → core / stage2_rule_store` の一方向。段階1と同じ約束。

`ambiguity_judge.py` は `population_rules.py` を import しない。`RuleResult` は
`.axes` / `.needs_clarification` / `.defaults_applied` を持つダックタイピングで扱う。
**各層が互いを知らない作りを保つため。**

## 4. 工程①の出力契約

### 4.1 本体プロンプト（`_PROMPT`、10行）

| 項目 | 取りうる値 | 何を表すか |
|---|---|---|
| `AGGREGATION` | `EVENT` / `ENTITY` | 集計対象が実績（売上・購入回数）か、マスタの行そのもの（店舗数・会員数）か |
| `GROUP_BY` | `MASTER_STORES` / `MASTER_MEMBERS` / `MASTER_PRODUCTS` / `TIME` / `FACT_COLUMN` / `NONE` | 出力を分けている軸の種類 |
| `GROUP_BY_GRANULARITY` | `IDENTITY` / `CLASSIFICATION` / `NA` | `MASTER_*` のとき、個体を識別する軸か、少数固定の分類列か |
| `LIMITED` | `YES` / `NO` | 件数を明示的に区切ったランキング（トップN）か |
| `GROUP_BY_RESOLVED` | `RESOLVED` / `UNRESOLVED` / `NA` | 実績の無いマスタ行・期間を0行として並べるかを質問文が明言しているか |
| `SYNONYM` | `NONE` / `region_RESOLVED` / `region_UNRESOLVED` / `channel_RESOLVED` / `channel_UNRESOLVED` | `region` / `channel` の表記ゆれを統合するかを明言しているか |
| `CATCHALL` | `NONE` / `pref_RESOLVED` / `pref_UNRESOLVED` / `gender_RESOLVED` / `gender_UNRESOLVED` | `pref` / `gender` の包括値・未回答の扱いを明言しているか |
| `PERIOD` | `NONE` / `YYYY-MM-DD..YYYY-MM-DD` | 対象期間（基準日から絶対日付に直した半開区間） |
| `REGION_FILTER` | `NONE` / `中国` / `中部` / `九州` / `北海道` / `東北` / `近畿` / `関東` / `関西` | `stores.region` の値で絞り込んでいるか |
| `RATE_DENOMINATOR` | `NONE` / `MASTER_STORES` / `MASTER_MEMBERS` / `MASTER_PRODUCTS` | 平均・比率の分母がマスタ実体の個数か |

### 4.2 `FLAG_*` プロンプト（`_FLAG_PROMPT`、3行）

| 項目 | 取りうる値 | 何を表すか |
|---|---|---|
| `FLAG_STORES` | `NONE` / `RESOLVED` / `UNRESOLVED` | `stores` がこの質問に関わるか、関わるならフラグ（`close_date`）の扱いを明言しているか |
| `FLAG_MEMBERS` | 同上 | `members`（`is_active`）について同じ |
| `FLAG_PRODUCTS` | 同上 | `products`（`is_discontinued`）について同じ |

`AxisExtraction` はこの13項目に加えて `raw_response` / `prompt` / `model` /
`prompt_tokens` / `completion_tokens` / `latency_ms` を持つが、**これらは計測用で
出力契約ではない。**

### 4.3 なぜプロンプトを2本に分けたか

**当初は1本（13行）だった。** 項目を1つ足すたびに、無関係なはずの別の項目
（多くは `FLAG_*`）が壊れる現象が3度続いた。切り分けの測定で、
`CATCHALL` の文言を戻すと `FLAG_MEMBERS` の分布が変わることを確認している
（n=20、`NONE` が 80% → 50%）。**項目同士がプロンプト内で相互作用していた。**

そこで `FLAG_STORES` / `FLAG_MEMBERS` / `FLAG_PRODUCTS` を本体から切り離し、
別プロンプト・別の LLM 呼び出しにした。本体の結果
（`AGGREGATION` / `GROUP_BY` / `GROUP_BY_GRANULARITY`）を `_FLAG_PROMPT` へ
渡す——2回の呼び出し間で「`GROUP_BY` は `MASTER_STORES` なのに `FLAG_STORES` が
`NONE`」のような食い違いが起きにくくするため。

呼び出し回数は1問あたり1回から2回に増えるが、実測（24問1回）ではトークンが
89,949 → 105,436（約 +17%）、所要時間は 69.6秒 → 70.3秒でほぼ変化しなかった。

**「①の脆さが無くなった」わけではない。** 本体側の項目同士の相互作用はこの変更では
直らない（8.3節）。分離の副作用として新たな誤りも生まれた——`GROUP_BY` が
`MASTER_*` だという事実を `FLAG_*` 側が「フラグの扱いを明言している」ことと取り違え、
グループ化されているだけの質問まで `RESOLVED` にしてしまった。**「関わる」ことと
「明言している」ことは別**という一文と3表分の具体例を `_FLAG_PROMPT` に足してある。

### 4.4 値域を正規表現に埋める

パースは項目ごとの正規表現で行い、**値の列挙そのものをパターンに埋め込んである。**

```
_GROUP_BY_RE = re.compile(
    r"GROUP_BY:\s*(MASTER_STORES|MASTER_MEMBERS|MASTER_PRODUCTS|TIME|FACT_COLUMN|NONE)",
    re.IGNORECASE,
)
```

契約外の値は「その行が見つからない」として扱われ、`LLMTransientError` になる。
**1行でも欠けるか値が不正なら、その1問は失敗として次へ送る**（段階2これまでの
失敗分類を流用し、新しい例外は作らない）。**黙って既定値に落とさない**——落とすと、
記録に残る構造と実際にモデルが答えた内容が食い違い、③の判定がどの入力から出たのか
追えなくなる。`RuleEvalSummary.failed` が 0 でなければ出力契約の不備の疑いである。

`GROUP_BY:` と `GROUP_BY_RESOLVED:` / `GROUP_BY_GRANULARITY:` を取り違えないことは
テストで固定してある。

### 4.5 プロンプトの版を記録する

`prompt_digest()`（本体）と `flag_prompt_digest()`（`FLAG_*` 用）を
`Nl2SqlStage2RuleExperiment` に保存する。**プロンプトの文言を1文字変えると値が変わる。**
評価データの `dataset_digest` と同じ考え方で、**版が違うプロンプトの実験は比較できない。**
2本のプロンプトを別々の列にしてあるので、どちらを触ったかが後から分かる。

## 5. 工程③の判定ロジック

`population_rules.classify()` は純コードで、LLM を呼ばない。
`AxisExtraction` を属性だけ見る（ダックタイピング）。

| 型 | 何を検出するか | 既定 | 実データ照会 |
|---|---|---|---|
| 1 | 結合欠落。実績の無い実体・期間を0行として並べるか | **置かない。聞き返す** | 要る |
| 2 | フラグ。閉店・退会・廃番の行を含めるか | 実体を数える→現役のみ／事象を集計→全部含める | 要る |
| 3 | 同義値。`region` の関西/近畿、`channel` の EC/オンライン | 統合する | 不要 |
| 4 | 包括値・NULL。`pref` / `gender` の「その他」「未回答」 | 除外せず独立区分として表示 | 不要 |

`RuleResult.needs_clarification` は **型1が1つでも未確定なら真。**
型2〜4は既定があるので聞き返さない。

### 5.1 型1（結合欠落）

成立するのは `AGGREGATION == "EVENT"` のときだけ。マスタ実体を数える質問
（`ENTITY`）に「実績ゼロの行を並べるか」という論点は無い。

そのうえで、次のいずれかで軸が立つ。

- `GROUP_BY` が `MASTER_*` **かつ** `GROUP_BY_GRANULARITY == "IDENTITY"`
  **かつ** `LIMITED != "YES"`
- （上に当たらないとき）`RATE_DENOMINATOR` が `MASTER_*` **かつ** `LIMITED != "YES"`
- （上のいずれにも当たらないとき）`GROUP_BY == "TIME"`

**分類列でのグループ化（`CLASSIFICATION`）を型1にしないのは**、値の種類が
あらかじめ少数に決まっており、行の欠落で分類そのものが丸ごと消えることが無いため。
**トップN形式（`LIMITED`）を型1にしないのは**、ランキングの外に出るだけの実体は
そもそも出力に現れるかどうかが結果を左右しないため。

`RATE_DENOMINATOR` の経路は「会員1人あたりの平均購入金額」のように、
**`GROUP_BY` がそのマスタ表を指していなくても平均・比率の分母がマスタ実体の
個数になっている**場合を拾う。

質問文が `GROUP_BY_RESOLVED: RESOLVED` を返していれば、その時点で解消。
そうでない場合に**実データ照会へ進む**（5.4節）。

### 5.2 型2（フラグ）

`FLAG_STORES` / `FLAG_MEMBERS` / `FLAG_PRODUCTS` が `NONE` でない表ごとに軸を立てる。
既定の向きは1行で決まる。

```
default_direction = "現役のみ" if extraction.aggregation == "ENTITY" else "全部含める"
```

**判定の鍵は「数える対象が実体か、事象か」であって、並べる軸が区分かどうかではない。**
「会員ランク別の会員数」は現役のみ、「会員ランク別の客単価」は全部含める。
論理は一貫しているが利用者には分かりにくいので、**開示文で必ず前提を示す**（6節）。

型2には2つの解消経路がある。どちらも近似規則ではなく実データ照会で決める。

- **同じマスタ表を型1が指しているとき**：フラグの立った実体が対象期間に実績を
  持たないなら、型2は型1と同じ集合を指している。**軸を別立てせず、型1に吸収する**
- **型1と別の表で、かつ `stores` で `REGION_FILTER` が `NONE` でないとき**：
  絞り込み後の集合にフラグの立った店舗が実在しなければ、その問い自体が空なので
  `resolved=True` にする（軸は残す）

### 5.3 型3（同義値）・型4（包括値・NULL）

`SYNONYM` / `CATCHALL` が `NONE` でなければ軸を立てる。`region_UNRESOLVED` のような
値を `_` で分割し、後半が `RESOLVED` かどうかだけを見る。**実データ照会はしない**
——列の値域は静的に分かっており、データ次第で変わらないため。

### 5.4 実データ照会（`flagged_activity.py`）

型1・型2の一部は、**列の一覧を見るだけの静的規則では決まらない。**
データ次第だからである。近似規則を置く代わりに `demo_readonly` への軽い照会を1本行い、
事実を直接確かめる。**ここで SQL を生成することはない**——固定のクエリだけを使う。

| 関数 | 何を確かめるか | どこで使うか |
|---|---|---|
| `check_flagged_activity(table, period, *, region_filter)` | フラグの立った実体が、その期間に実績を持つか | 型2の吸収判定・`region` 絞り込み後の解消判定 |
| `has_unrepresented_entity(table, *, active_only, period, region_filter)` | 対象の母集合に、その期間で実績ゼロの実体が実在するか | 型1（マスタ実体）を立てる根拠 |
| `has_unrepresented_time_unit(period)` | 対象期間に、実績ゼロの暦日が実在するか | 型1（時間軸）を立てる根拠 |

**`check_flagged_activity` が見る集合と `has_unrepresented_entity` が見る集合は違う。**
前者は「フラグが立った行」、後者は「（絞り込み後の）母集合全体」。同じ関数にできないので
別に分けてある。

いずれも**実在しなければ軸を立てない**、という向きに使う。実績ゼロの実体が居ないなら、
型1を立てても出力の顔ぶれは変わらない——**問い自体が空である。**
`has_unrepresented_time_unit` が**暦日**だけを見て粒度（日・月・年）を①から
受け取らないのは包含関係による。日次で網羅されていれば、それを含むどの月・年も
必ず実績を持つ。

3関数とも、実データの既知の事実で両分岐を固定してある（`test_flagged_activity.py`）。

| 確かめている事実 | 値 |
|---|---|
| 営業中の店舗のうち実績ゼロ | 0店（37店中） |
| 在籍中の会員のうち実績ゼロ | 1,560人（17,076人中） |
| 閉店店舗の所在（関西／近畿） | 0件（全3件は九州・中国・北海道） |
| 実績範囲 2024-08-15〜2026-08-14 の実績ゼロの暦日 | 0日 |

**依存性注入にしてある。** `classify()` は3つの checker を引数で受け取り、
`None` なら照会をせずフォールバックの挙動（型1・型2を常に別々に立てる）になる。
テストは `None` かフェイクを渡し、DB に触れない。本番の既定は
`stage2_rule_services.run_stage2_rule_experiment` で本物の照会関数を差す。

## 6. 工程②の開示文

### 6.1 「聞き返す」ではなく「既定を明示して答える」

**素の業務質問は7割で母集合が未確定である**（段階1の35問を確定基準で数え直して
25問。`docs/AD_Nl2Sql_Design.md` 8節）。**7割で聞き返すシステムは使い物にならない。**

一方、黙って解釈すれば「抜けた行」がそのまま起きる。この案件の原点にある
「関西の売上が落ちています」の裏で「近畿」表記の店舗が抜けていた、という害である。

そこで、**答えを返したうえで、当てた既定と、それを変える手段を示す。**
聞き返すのは既定を決められない型1だけに絞る。

### 6.2 どちら向きの既定でも開示する

**除外を黙るのと同じく、含めたことを黙るのも同じ害になる。** 統合したことも、
独立区分として出したことも同様。プロンプトの「書き方」節で次を課している。

- 開示は先に書く。何を前提にしたかを必ず告げる（黙ってはいけない）
- 開示した既定には**変える手段を必ず1文添える。** 既定を宣言するだけで終えない
- 「確認したいこと」があれば、開示のあとに確認の質問を1文添える。無ければ書かない
- 列名・テーブル名のような英数字の識別子は使わず、日本語の業務の言葉で書く

### 6.3 監査用の名前を利用者向けの言葉へ変換する

`RuleAxis.name` は `stores.close_date` / `店舗の母集合（結合欠落）` のような
**監査用の識別子**で、利用者向けの文にそのまま出す語ではない。
②へ渡す前に業務の言葉へ変換する（`_AXIS_DISPLAY_NAME`）。`stores.close_date` は
「閉店した店舗」、`店舗の母集合（結合欠落）` は「売上の無い店舗を並べるかどうか」。
対象になりうる名前は③側の列挙で尽くされている（有限）。未知の名前はそのまま返す
フェイルセーフにしてある。

既定の適用も型1の未確定も無ければ、`phrase_disclosure` は LLM を呼ばず空文字を返す。
**新しい判断はここではしない**——③はすでに終わっている。

## 7. 採点

### 7.1 コードで採点する意味

`rule_scoring.py` は `stage2_rule_evaluator.evaluate()` の戻り値、または
保存済み明細（`stage2_rule_store.read_details()`）を正解ラベルと突き合わせて数字を出す。

**受け入れ側が、同じ入力から同じ数字を独立に再現できる。**
`items_from_details()` があるので、**API を再び呼ばずに採点だけをやり直せる。**
人が目視で数えた数字は、数え直すたびに変わりうる。

判定ロジック（`axis_extractor.py` / `population_rules.py`）には一切触れない。
`evaluate()` の戻り値も変えていない——採点は別関数として足しただけ。

### 7.2 指標

検出型の集合は `item.axes` のうち `resolved=False` のものの `kind` から求める。

| 指標 | 定義 |
|---|---|
| **型の完全一致** | 検出型の集合 == 正解の `types` 集合（**主指標**） |
| 「聞き返すか否か」一致 | 型1の有無が正解と一致 |
| 見逃し（型別） | 正解にあり判定に無い型 |
| 過検出（型別） | 判定にあり正解に無い型 |

**副指標を型別に出すのは、全体の数字だけでは次の手が決まらないため。**
段階1でタグ別の内訳を必ず出すのと同じ理由。

`unscored_ids`（正解側と突き合わせられなかった `id`）は本来空であるべきで、
**0でなければ評価データと明細の対応が壊れているサイン。**

### 7.3 実験1回の記録

`Nl2SqlStage2RuleExperiment` に集計、明細はファイル（`NL2SQL_STAGE2_RULE_LOGS_DIR`）。
「集計はDB、明細はファイル」の分担は段階1と同じ。**置き場のキーは他の段階2ログと
別にしてある**——同じキーを使うと、片方だけテストで上書きしても他方に事故が及ぶ。

`dataset_digest` の対象は `id` と `question` のみ。**正解ラベル（`types`）を
含めない**——ラベルの読み方を直しても、同じ質問セットで測った実験どうしは
比較できたままにしておくため。

## 8. 既知の構造的限界

**調整では直らないものだけを挙げる。** いずれも出力契約の構造に由来する。

### 8.1 `GROUP_BY` は複数の軸を同時に表現できない

`GROUP_BY` は6値の**単一値**しか取れない。「店舗ごとに、月別の」のように
マスタ実体の軸と時間の軸を同時に求める質問には、1つしか答えられない。

**なぜ直せないか。** 契約が単一値の列挙で、パーサは正規表現で最初に一致した1つを拾う。
モデルが `MASTER_STORES / TIME` と2値を返しても、先頭だけが残る。
プロンプトの言い回しで補おうとすると、`FLAG_*` の判定を別の場所で壊す。
実際、この目的で足した追記は、既に安定していた別の確認を
6/6 からほぼ 0/16 まで崩したため取り下げた。

**取り下げた後も元には戻っていない。** 「店舗の開店年別に、店舗数の推移を教えて
ください。」は現行で **28回中5回（約18%）**しか `TIME` にならない（追記前は 6/6）。
同じ規則でも「商品の発売年別に、新商品の登録点数を」は 12/12 で維持されており、
**壊れているのは実体を数える形だけである。**

**直すなら `GROUP_BY` が複数軸を同時表現できるよう出力契約自体を見直す必要がある。**
契約が変わるため、**変更後は未知データで測り直すこと。**

### 8.2 `CATCHALL` は `pref` と `gender` の2列しか見ていない

`CATCHALL` が取りうる値は `NONE` と `pref` / `gender` × `RESOLVED` / `UNRESOLVED` の
5つだけ。**包括値・欠測を持つ他の列は、そもそも列挙に存在しない。**

**なぜ直せないか。** 検出範囲が値域そのもので決まっているため、
プロンプトの言い回しをどう変えても列挙に無い列は出力できない。

盲検で実際に外れている。「会員の年代別の会員数」は型4が立たない。
「年代」は `members.birth_date` から導く派生区分で、`birth_date` の NULL は 5,980件
あるが、**その列が対象に入っていない**（詳細は `docs/AD_Nl2Sql_Design.md` 8節）。

同じ構造の限界が型3にもある。`SYNONYM` の対象は `region` と `channel` の2列だけ。

**直すなら、派生区分と、包括値・NULL を持ちうる他の列を対象へ加える必要がある。**
出力契約が変わるため、**変更後は未知データで測り直すこと。**

### 8.3 ①は同一条件でも揺れる

温度 0.0 でも、①の出力は反復で割れる。**判定（③）を決定論にしても、
その入力を作る①は決定論ではない。**

| 観測 | 値 |
|---|---|
| `CATCHALL` の文言を戻すと `FLAG_MEMBERS` の分布が変わる | `NONE` 80% → 50%（n=20） |
| `SYNONYM` への追記が `店舗別` の `FLAG_STORES` を崩す | 20/20 →（`UNRESOLVED` 3/5・`NONE` 2/5、約60%） |
| 91件の全量突き合わせでの型完全一致 | 48〜51/91 →（改善後）68〜69/91 |

**なぜ直せないか。** 項目同士がプロンプト内で相互作用しており、1項目への追記が
無関係なはずの別項目の分布を変える。`FLAG_*` を別プロンプトへ切り出したのは
この相互作用を減らすためだが（4.3節）、**本体側の項目同士の相互作用はこの変更では
直らない。**

したがって、**単発の測定値を「1回の値」として断定的に書かない。**
常設テストも、安定して通る言い回しだけを置き、不安定なものは通る文を選び直すのではなく
テスト自体を置かない方針にしてある。

### 8.4 型1の3経路は排他である

`classify()` の型1判定は `if / elif / elif` で、**最初に成立した1経路だけが軸を立てる。**
`GROUP_BY` がマスタ軸なら `RATE_DENOMINATOR` は見ない。`RATE_DENOMINATOR` が
マスタ実体を指していれば `GROUP_BY == "TIME"` の分岐へは進まない。

同じ質問が「時間軸のロスター」と「母数のロスター」の両方を未確定にしている場合、
**片方しか立たない。** 8.1 と同じ根で、1つの `GROUP_BY` に軸を1つしか
持たせられない契約の帰結である。

### 8.5 実データ照会は `demo_sales` に固定である

`flagged_activity.py` のクエリは表名・列名・結合条件をすべて直書きしてある。
**他のスキーマへはそのまま移せない。** これは意図した割り切りで、
「質問文から SQL を組み立てる」経路を③に持ち込まないための条件でもある。

同じ理由で、絞り込み後の集合を確かめる経路は `stores.region` だけに用意してある。
**他の列・他の表への一般化はしていない。** 表記ゆれ（関西/近畿）も
`_REGION_SYNONYMS` に直書きした既知の事実で、一般の同義語解決ではない。

### 8.6 型2の吸収は監査ログに残らない

型1へ吸収された型2は、軸そのものを作らずに `continue` する。
一方 `REGION_FILTER` 経由の解消は `resolved=True` の軸として残る。
採点上はどちらも「未確定として検出していない」で同じだが、
**明細を読んだときに「吸収されたのか、そもそも検出されなかったのか」が区別できない。**
